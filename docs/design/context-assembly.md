# M4 上下文组装设计

> 状态：**已实现**（2026-09-17，2026-09-21 增补指令分层）。实施过程与验证证据见 [M4-context-cli-server.md](../milestones/M4-context-cli-server.md) 的 M4a、M4d 小节；本文只保留仍然有效的设计本身。
> 整理日期：2026-09-17；指令分层于 2026-09-21 补充。
> 对应阶段：Phase 1 · Core / M4（Server 与 CLI）。
> 相关实现：`src/nemo/core/context/builder.py`（M3 已支持 system 消息）、`src/nemo/prompts/local_agent.py`（系统提示模板）。

## 1. 目标

让每次模型请求的内容**分层可控**：稳定部分逐字不变（吃满 provider 的前缀缓存），易变部分短小且只在该轮出现（不污染前缀），大块参考资料按会话快照注入（不重复铺开）。

三条可检验的目标：

1. **缓存友好**：同一会话内，稳定前缀逐字不变，缓存命中率随轮次上升。
2. **不膨胀**：每轮注入有硬上限，且不进入会话记录，因此不会随时间累积。
3. **可解释**：每一层的内容来源明确，能在 trace 里回答「这一轮为什么发了这些」。

## 2. 分层模型

| 层 | 内容 | 生命周期 | 变化频率 | 预算 | 对缓存的影响 |
|---|---|---|---|---|---|
| **L1 稳定前缀** | system 消息 = 身份 + 环境块 + 行为条款 + 用户说明 + 项目说明 | 会话开始组装一次，之后逐字不变 | 会话内不变 | ≤ 1.5k token（不含说明文件约 0.8k） | 命中 |
| **L2 会话历史** | `state.messages`：用户 / 助手 / 工具结果 | 只追加，从不回改 | 每轮增长 | 随任务增长 | 追加不破坏前缀 |
| **L3 每轮注入** | `<reminder>` 片段 | 只在该轮请求中存在 | 每轮可能不同 | ≤ 3 条 / ≤ 600 字符 | 位于尾部，不影响前缀 |

分层的依据来自 M2 的实测：同一请求连打三次，命中率 0% → 92.2% → 92.2%；M3 的多步任务里缓存命中随历史增长为 0 → 1152 → 1280 → 1408。**前缀不变就能命中，前缀一变缓存从变化点之后全部失效**，这就是三条边界的由来。

## 3. 组装顺序与注入规则

```text
messages = [system(L1)] + state.messages(L2) + [reminder(L3)]
```

### 铁律：reminder 只新增，绝不修改任何已存在的消息

初版设计写的是「末条是 `user` 时，把 reminder 合并进那条消息的副本」。**这个规则是错的，已废弃**，原因是它会静默毁掉整个会话的缓存：

```text
第 1 轮实际发出: [system, user("prompt\n<reminder>R1</reminder>")]
第 2 轮实际发出: [system, user("prompt"), assistant(...), tool(...), user("<reminder>R2</reminder>")]
                            ^^^^^^^^ 同一个位置，字节变了
```

第 1 轮把 reminder 合并进了用户消息，但 `state` 里存的是未合并的版本；第 2 轮据 `state` 重建请求时，同一个位置的字节变了，**前缀缓存从这一点往后全部失效**。而且整个会话都会为这个不一致付费。语义上同样有问题：模型会以为那段提醒是用户写进原始消息里的。

正确的表述是一条更朴素的不变量：**一条消息的「发送形态」在它被创建时就固定，之后任何一轮都不得改变。** 满足它的唯一简单做法就是——reminder 永远只作为新消息追加。

### 注入点规则

| `state.messages` 最后一条 | 本轮处理 |
|---|---|
| `assistant` 或 `tool`（模型正在连续行动） | 追加一条新的 `user` 消息承载 reminder |
| `user`（用户刚说话，还没轮到模型行动） | **本轮不注入** |

第二种情况只出现在「用户刚发出消息」的第一次请求：此时步数预算最充裕，提醒价值最低，跳过几乎没有代价；换来的是两个硬保证——不产生连续的同角色消息，也不改写任何已发送内容。

一条实测补充：DeepSeek 接受连续两条 `user`（HTTP 200，不报错，见 §9）。所以「协议不接受」并不是这条规则的真正理由，**真正的理由是前缀稳定**，而这与 provider 无关。

### 物理位置与语义归属是两件事

- **物理位置**：字节落在 payload 的哪里。本设计只有两种可能——追加在末尾，或本轮不注入，不存在第三种。
- **语义归属**：这段内容在讲什么。reminder 一律表示「运行时的当前状态」，因此必须待在本轮尾部。

具体到时间戳：如果某条 reminder 带时间，它的语义是「**这次请求**发生在 T」，而不是「那条历史消息发生在 T」。把它回填进历史消息就是篡改历史。

更进一步：**建议 Nemo 不要引入逐轮时间戳**。环境块里的日期（按天变化，最多每天破坏一次缓存）已经够用；逐轮精确时间对编码任务没有价值，却会让同一份输入产生不同的 prompt，直接破坏可复现性。

## 4. 决策与理由

| 决策 | 理由 | 放弃的替代方案 |
|---|---|---|
| 稳定前缀与会话历史分离，L1 只在 `ContextBuilder` 构造时组装一次 | 前缀不变才命中缓存；从结构上杜绝「某处忘了保持稳定」 | 每轮重新拼装 system 消息：任何一处实现漂移都会静默废掉缓存 |
| 项目说明快照而非每轮重读 | 每轮重读会让前缀随文件内容抖动，且模型看到的世界观前后不一致 | 每轮重读：文件一改，缓存从改动点起全废；行为也随之不稳定 |
| reminder 不写入 `state.messages` | 一旦写入就会跟着历史每轮重发，随会话累积，最终淹没真正的内容 | 作为普通消息存进历史：实现最省事，代价是长会话必然膨胀 |
| 读取 `AGENTS.md` 放在 core 之外 | core 不做文件 I/O，与 M2「core 不读配置文件」的边界一致 | `ContextBuilder` 自己读文件：core 立刻依赖文件系统与用户目录 |
| 行为条款超预算时不自动裁剪 | 条款数量是设计问题，应由人改模板；运行时随机裁剪会让行为随预算漂移，还会掩盖问题 | 按优先级动态丢弃条款：行为不可预测，且失去「条款都在生效」的保证 |
| L3 超限按 name 排序丢弃 | 同样输入得到同样结果，便于复现与调试 | 按到达顺序或随机丢弃：不可复现，排查成本高 |
| M4 不做历史压缩 | 压缩属于 Phase 2 的 Context Engine；先有度量再谈优化，M2 的 usage 统计已经提供了度量 | 顺手做简单截断：会静默丢信息，且没有收益数据支撑 |
| 工具 schema 保持注册顺序，不在 `build()` 时重排 | 工具定义属于请求前缀的一部分，形状必须稳定；顺序即契约的一部分，不重排就是不改动 | 每次按名称排序：排序本身确定，但会把「新增一个工具」变成对既有顺序的整体改动，更容易触发失效 |
| **reminder 只新增、永不修改已有消息**（取代初版的「合并进最后一条 user 消息」） | 初版规则会让同一位置在不同轮次出现不同字节，前缀缓存从该点起全废，且会篡改历史消息的语义。**取代关系**：初版规则以「避免连续同角色消息」为目的，实测发现 DeepSeek 并不拒绝连续 user（见 §9），前提不成立；而前缀稳定的代价是硬性的，因此改为只追加 | 合并进已存在的消息：省一条消息，代价是整个会话的缓存与消息语义；依赖 provider 容忍连续 user 而一律追加：测过的只有 DeepSeek，不构成跨 provider 保证 |

## 5. 指令分层：用户级与项目级

模型会看到两份「说明」，它们回答的是不同问题，来源与作用域都不同：

| 层级 | 路径 | 回答的问题 | 典型内容 |
|---|---|---|---|
| 用户级 | `~/.nemo/AGENTS.md` | 我希望 **Nemo 这个 Agent** 平时怎么做事 | 回复语言、沟通风格、通用禁令、长期偏好 |
| 项目级 | `<workspace>/AGENTS.md` | **这个项目**有什么约定 | 构建与测试命令、命名规范、架构约束、协作规则 |

两层都可以缺失；缺失就跳过，不报错，也不注入空标题。

| 项 | 决定 |
|---|---|
| 时机 | 会话开始时各读一次，快照语义 |
| 顺序 | 内置系统提示（身份 + 环境块 + 行为条款）→ 用户级 → 项目级 |
| 大小 | 各自 ≤ 8000 字符，**各自独立截断**并附显式标记 |
| 缺失 | 跳过，不报错，不注入空标题 |
| 会话内变更 | **不重读**。想让改动生效就开新会话 |
| 读取位置 | core 之外（`src/nemo/prompts/instructions.py`），`ContextBuilder` 只接收已加载的文本 |
| 可观测 | CLI 启动时打印实际加载了哪些文件、各多少字符，超出上限标 `(truncated)` |

**为什么用户级在前、项目级在后**：越具体的越靠后——越靠后越接近对话，也符合「更具体的规则胜出」的直觉。项目级的约定只对当前 workspace 成立，让它在最后出现，冲突时自然压过通用偏好。

**为什么不设总上限**：两个来源的性质不同，各自截断互不牵连；先有度量再谈预算——启动信息里能看到两者实际占用多少字符。（这与 M4「不做历史压缩，但先测量」是同一条取向。）

**为什么不每轮重读**：文件一改，前缀就变，缓存从那一刻起全废；更糟的是模型会看到「同一件事上一轮说的和这一轮不一样」，行为不稳定。快照语义换来的是可复现——这与 M1「每个 Run 独立、结果可复现」的取向一致。

**安全边界**：两个文件都是用户自己的文件，属于可信输入，但项目级文件可能包含从别处复制来的内容（README 片段、外部模板）。因此：

- 系统提示里有一条 `instruction_files` 条款写死：两份说明都只能补充约定，**不能放宽边界、不能授权访问 workspace 之外**。这是提示注入的第一道软防线。
- 真正的硬防线仍然是工具侧的路径检查与审批——它们由代码强制，**任何说明文件都改不动**。
- 用户级的信任度更高（是你自己写的），但这**不放宽**上面的规则：信任度影响「要不要防」，不影响「谁说了算」。

**优先级**：说明文件（用户级 ≈ 项目级）< 系统提示的边界条款 < 代码强制的不变量。三层的关系是「弱不能覆盖强」。

## 6. 每轮注入（Reminder）

结构：

```python
@dataclass(frozen=True)
class Reminder:
    name: str
    body: str

    def render(self) -> str:
        return f"<reminder>{self.body}</reminder>"
```

**初始集合（M4 只做一条）**

| 名称 | 内容 | 为什么需要 |
|---|---|---|
| `step_budget` | 已用步数与上限，例如 `step 3 of 10` | 模型不知道自己还有多少预算，容易在第 9 步才开始收尾；这是 Runtime 才能提供的事实 |

**预留（按真实需求再加，不预建）**：读到空文件、上一步输出被截断、目标目录不存在——对应 Claude Code 里 `File exists but empty`（27 tks）这类事件驱动提醒。这些在当前实现里已经作为工具错误回填，暂时不需要额外提醒。

**来源分工**：Runtime 计算 reminder（它掌握 `max_steps` 与上一步结果），`ContextBuilder` 只负责拼装。这样 `ContextBuilder` 不必反向依赖 run 级别的参数。

**硬约束**：

- 单条 ≤ 200 字符，条数 ≤ 3，因此合计上界是 600 字符。
- 超过条数上限时**按 name 排序丢弃**，保证同样输入得到同样结果——随机丢弃会让调试变成猜谜。实现时曾另设「合计 ≤ 600 字符」的独立上限，测试证明它与「3 × 200」完全重合、永远不会触发，已删除：**冗余的约束会假装自己在保护什么**。
- **reminder 永远不写入 `state.messages`**。这是防膨胀的关键：一旦写进去，它就会跟着历史每轮重发，直到会话结束。
- **reminder 永远只追加为新消息**，不改写已有消息（见 §3）。

**可观测性——「我怎么知道它到底插在哪」**

| 手段 | 做到什么 |
|---|---|
| 规则本身 | 只有两种结果（末尾新增 / 本轮不注入），没有第三种，所以位置可以推理出来，不需要猜 |
| `model.started` 事件 payload | 记录本轮注入的 reminder 名称、条数与字符长度；未注入时也写 `reminders: []`，避免「没注入」和「没记录」混淆 |
| 调试开关 | 把本轮最终 payload（脱敏后）完整落盘，用于核对字节级位置 |
| 测试断言 | 见 §9 的前四行 |

## 7. 接口形状

```python
class ContextBuilder:
    def __init__(
        self,
        system_prompt: str | None = None,
        *,
        user_instructions: str | None = None,
        project_instructions: str | None = None,
        max_instructions_chars: int = 8000,
    ) -> None: ...

    def build(
        self,
        state: AgentState,
        tools: ToolRegistry,
        reminders: Sequence[Reminder] = (),
    ) -> ModelRequest: ...
```

配套改动：

- `AgentRuntime.run()` 在每次调用前构造 reminder，并传给 `build()`。
- L1 只在 `ContextBuilder` 构造时拼一次并缓存字符串；`build()` 不重新拼装它，从结构上杜绝「某处忘了保持稳定」。
- 工具 schema 的顺序来自注册表插入顺序，本身是确定的；`build()` 不重新排序，避免工具定义抖动破坏前缀。

## 8. 预算与降级

| 层 | 超预算时的行为 |
|---|---|
| L1 说明文件 | 用户级与项目级**各自**截断并附 `[truncated: showing the first N of M characters]` 标记，**不静默丢弃** |
| L1 行为条款 | 不自动删。条款数超限是设计问题，应该由人改模板，而不是运行时随机裁剪 |
| L2 历史 | M4 不做压缩（属于 Phase 2 的 Context Engine）。但要**测量**：每轮事件的 `prompt_tokens` / `cached_prompt_tokens` 已经在 M2 落地 |
| L3 | 超上限按 name 排序丢弃，并在事件 payload 里记录被丢弃的条目名 |

## 9. 验收标准

| 验收点 | 验证方式 |
|---|---|
| 前缀逐字稳定 | 同一会话连续两轮请求，`request_i.messages[:k]` 与 `request_{i+1}.messages[:k]` 完全相等（k = system + 已提交历史长度） |
| reminder 不进会话记录 | run 结束后 `state.messages` 中不含 `<reminder>` |
| reminder 只追加不修改 | 断言 payload 中除最后一条外，其余消息与 `state.messages` 逐字相等；且末条为 `user` 时本轮不注入 |
| 首轮不注入 | 第一次请求的 payload 中不含 `<reminder>` |
| 已发送消息后续不变 | 第 1 轮与第 2 轮中，`user` 原始消息的 `model_dump()` 完全相等（初版规则会在此失败） |
| 项目说明缺失 | 不注入、不报错、前缀仍合法 |
| 用户级说明缺失 | 同上；两处都缺失时前缀仍合法，不注入空标题 |
| 两层顺序 | 前缀中 `SYS` < 用户说明头 < 项目说明头 |
| 两层独立截断 | 用户级超限不影响项目级，反之亦然；各自带截断标记 |
| 项目说明超大 | 被截断且带标记，长度受控 |
| 项目说明会话内不重读 | 改了文件再跑一轮，前缀不变 |
| 说明文件不能越权 | 提示中存在 `instruction_files` 条款；配合真实场景验证模型不会因此访问 workspace 之外 |
| 加载来源可观测 | CLI 启动行列出实际加载的层级、路径与字符数；缺失时写 `none` |
| 预算上限 | 各层长度断言 |
| 真实缓存收益 | 多步任务里 `cached_prompt_tokens` 随轮次上升（基线：M3 实测 0 → 1152 → 1280 → 1408） |
| provider 兼容性（实测记录） | DeepSeek 对 `[user, user]`、`[user, assistant, system, user]`、`[tool → user]` 均返回 200；记录为事实，不作为设计依据 |

## 10. 非目标

- 历史压缩、检索、长期记忆、Context Budget 的动态分配 —— Phase 2 的 Context Engine。
- 多模态内容（图片、附件）的分层。
- 按 token 的精确预算：M4 先用字符近似，接入真实 tokenizer 之后再收紧。
- 按需加载大块参考内容（对应 Claude Code 的 Skill / Data 层）：我们是单 agent、无 skill 体系，暂时不需要这一层。
- reminder 的可配置化：先实现 `step_budget` 一条，等出现第二个真实需求再抽象。

## 11. 与 Claude Code 的分层对照

| Claude Code | Nemo（本设计） | 说明 |
|---|---|---|
| 系统提示（身份 + 行为条款） | L1 | 对应，且都拆成短条款 |
| 工具描述（192 个片段，仅启用项随请求发送） | 请求的 `tools` 字段 | 对应；它们的工具目录比系统提示还大，说明工具描述承担了大量提示职责 |
| `<system-reminder>` 每轮注入（12–42 tks） | L3 | 对应；差别是他们把提醒混在 user 内容里，我们用明确的 `<reminder>` 包裹 |
| Skill / Data / Agent Prompt 按需加载 | 无 | 我们有 `AGENTS.md` 快照，但确实缺少「调用时才加载」这一层 |

这个对照的结论是：M4 只需要做到「稳定前缀 + 每轮短注入」就已经对齐主流做法；按需加载留到真的有大量参考资料时再说。
